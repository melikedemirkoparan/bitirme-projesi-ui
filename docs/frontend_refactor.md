# Frontend Refactor Note for Claude

## Context
We already have an existing frontend prototype implemented in plain JavaScript and CSS.

This prototype is useful as a **UI and interaction skeleton**, but it does **not** fully match the finalized product model, database design, and workflow decisions.

Claude should treat the current frontend as a **starting point to refactor**, not as the final source of truth.

The visual prototype is reusable.
The product logic must be aligned with the finalized system design.

---

## High-level instruction
Reuse the existing frontend where it is helpful, especially for:
- visual layout
- page structure
- dark theme styling
- modal patterns
- basic navigation flow

However, refactor the frontend data model, page logic, and interaction behavior so they match the finalized application design.

Do **not** preserve incorrect frontend assumptions simply because they exist in the current prototype.

When the current prototype conflicts with the agreed product/database design:
- follow the finalized design
- do not preserve outdated prototype logic

---

## What must be changed
The following parts of the current frontend are not aligned with the finalized system and must be refactored.

### 1. Claim model must be expanded
The prototype currently treats a claim too simply.

The finalized claim model must support at least:
- `claim_id`
- `patent_id`
- `claim_number`
- `claim_dependency_type`
- `claim_category`
- `parent_claim_id`
- `claim_text`

A claim is **not** just a display name plus a local element array.

The frontend source of truth must reflect the real claim model.

---

### 2. Element model must be expanded
The prototype currently stores only lightweight element data.

The finalized element model must support at least:
- `element_id`
- `patent_id`
- `element_name`
- `reference_number`
- `definition_text`

Elements must be treated as first-class records belonging to a patent project.

They are not just temporary UI-only items.

---

### 3. Claim-to-element linking must follow the relation-table model
The current prototype keeps elements nested directly inside claims.

This does not match the finalized database design.

The finalized system uses:
- `claims`
- `elements`
- `claim_elements`

Therefore, Claude must refactor the frontend logic so that claim-element linking follows the relation-table model.

Even if the UI still renders elements inside a claim panel for usability, the underlying source of truth must align with:
- `claims`
- `elements`
- `claim_elements`

Do **not** model elements as permanently claim-owned nested records in the actual data logic.

---

### 4. Add Claim flow must use a modal
The current prototype adds a claim immediately.

This is no longer correct.

The finalized product requires an Add Claim modal that captures:
- `claim_dependency_type`
  - `independent`
  - `dependent`
- `claim_category`
  - `apparatus`
  - `method`
- `parent_claim_id` when the claim is dependent

This metadata must be part of the claim creation flow.

If needed, `claim_number` may be generated by the system based on claim order.

---

### 5. Element Definition modal must support structured editing
The current prototype displays element information too lightly.

The finalized modal must support:
- viewing `element_id`
- editing or entering `reference_number`
- editing `definition_text`
- later triggering `AI Suggested Definition`

Clarification:
- `element_id` is view-only
- `reference_number` is editable
- `definition_text` is editable

The user must always remain able to write or edit the final definition manually.

---

### 6. Extraction Queue must be editable
The queue is not a passive AI output list.

It must support:
- showing extracted elements
- manually adding missed elements
- deleting incorrect extracted elements
- opening an element definition editor
- later integrating with the automatic extraction module

Claude should preserve the queue concept but ensure it behaves as an editable curation area.

---

### 7. Draft Composer must match the simplified V1 rule
The current draft composer prototype is useful as a base, but the behavior must follow the agreed specification.

For V1:
- `Selected Claims` means **all claims currently saved in the active project**
- there is **no** manual claim picking UI required in V1
- `Sections` and `Citations` panels are not needed
- `Generate Draft` is intended to trigger the future full patent drafting module

The page should prepare for this workflow instead of preserving misleading placeholder subpanels.

---

### 8. Upload flow terminology and routing must be updated
The current prototype refers to embedding/index creation in a way that does not match the finalized system direction.

The finalized system direction is:
- the user clicks `Upload Data` from the navbar
- the user is routed to a dedicated Excel upload page
- uploaded Excel data is processed later by ingestion/indexing modules
- a vector database is created using **ChromaDB**

Claude should update terminology and integration assumptions accordingly.

Do **not** keep FAISS-specific wording if the product direction is ChromaDB.

---

## State management refactor guidance
The prototype state can be used as inspiration, but it must be reorganized to reflect the finalized domain model more accurately.

Claude should move toward a structure conceptually closer to:
- current project / patent
- claims
- elements
- claim-element links
- patent draft
- upload / indexing status

The important rule is:

**Frontend state should mirror the real backend/domain model as closely as practical.**

## Styling guidance
Claude may preserve most of the CSS design language because it already fits the intended product direction.

This includes:
- navbar/topbar style
- dashboard style
- panel structure
- modal appearance
- dark theme tokens

Only targeted styling changes should be made where the UI now requires:
- new modal fields
- editable reference number inputs
- upload page integration
- updated navigation labels
- updated status badges

---

## Priority order
When refactoring the frontend, Claude should prioritize in this order:

1. align frontend logic with the finalized backend/domain model
2. preserve visual continuity where possible
3. implement correct modal-based workflows
4. remove outdated prototype assumptions
5. prepare future integration points without faking unfinished modules

---

## Final instruction to Claude
Treat the existing frontend as a strong **prototype UI base**, but align all logic with the finalized application design.

The visual prototype is reusable.
The product logic must be corrected.

The frontend source of truth must follow the finalized system design, even if some UI components temporarily render simplified views.
